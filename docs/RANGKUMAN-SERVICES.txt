================================================================================
  RANGKUMAN SERVICE FNBSense  —  IAM, CATALOG, ORDERING, REALTIME & INVENTORY
  Update: 2026-07-19
================================================================================

FNBSense = "OS cafe" multi-tenant (banyak cafe dalam satu sistem).
Arsitektur: microservice — tiap fungsi jadi service terpisah, DB sendiri-sendiri.
Sampai sekarang ada 5 service: IAM, Catalog, Ordering, Realtime, dan Inventory.

Istilah penting:
  - Tenant  = satu cafe/bisnis. Semua data "dicap" milik tenant tertentu.
  - JWT     = "KTP digital" (token) yang membuktikan siapa kamu, cafe mana,
              dan jabatanmu. Diterbitkan IAM saat login.
  - RS256   = cara tanda tangan token pakai sepasang kunci:
              PRIVATE key (rahasia, cuma IAM) buat menandatangani,
              PUBLIC key (boleh dibagi) buat memverifikasi.


================================================================================
  SERVICE 1 — IAM  (Identity & Access Management)
================================================================================

TUJUAN
  Gerbang identitas. Ngurus daftar akun, login, dan menerbitkan "KTP digital"
  (token). Semua service lain percaya token dari IAM.

KONFIGURASI
  - Laravel 13, PHP 8.3+
  - Database: MySQL "fnbsense_iam"
  - Port: 8000
  - Auth: JWT RS256 (IAM PEGANG private + public key)
  - 2 jabatan (role): owner (pemilik cafe) & cashier (kasir)

ENDPOINT
  PUBLIK (dibatasi 6 request/menit, anti brute-force):
    POST /api/auth/register  -> daftar cafe baru + akun owner sekaligus
    POST /api/auth/login     -> masuk, dapat token

  WAJIB TOKEN:
    GET  /api/auth/me        -> lihat data diri (siapa saya)
    POST /api/auth/logout    -> keluar (token diblacklist/dibatalkan)
    POST /api/auth/refresh   -> perpanjang token

ALUR SINGKAT
    Register  -> IAM bikin tenant (cafe) + user owner -> kasih token
    Login     -> IAM cek email+password -> kasih token berisi:
                 { siapa (user id), cafe mana (tenant_id), jabatan (role) }

KEAMANAN
  - Password di-hash, gak pernah disimpan mentah.
  - Token ditandatangani private key (gak bisa dipalsuin).
  - Gagal login gak bocorin akun mana yang salah.
  - Anti privilege escalation: role & tenant dipaksa server, bukan dari input.
  - Catatan yang ditunda: services/iam/SECURITY_TODO.md

STATUS: SELESAI + teruji (11 feature test). Sudah di-commit.


================================================================================
  SERVICE 2 — CATALOG  (Menu & Produk)
================================================================================

TUJUAN
  "Otak menu" — sumber kebenaran APA YANG DIJUAL tiap cafe (kategori, produk,
  harga). Dipakai: customer (lihat menu), Ordering (ambil produk buat pesanan),
  dashboard owner (kelola menu).

KONFIGURASI
  - Laravel 13, PHP 8.3+
  - Database: MySQL "fnbsense_catalog" (+ "fnbsense_catalog_test" buat test)
  - Port: 8001
  - Auth: JWT RS256 STATELESS -> Catalog CUMA punya PUBLIC key IAM.
          Artinya: Catalog bisa MEMVERIFIKASI token, tapi TIDAK bisa
          menerbitkan token, dan TIDAK pernah nanya ke IAM. Ringan & aman.
  - Blacklist dimatikan (urusan logout ada di IAM).

STRUKTUR DATA
  Tabel "categories": id, tenant_id, name, sort_order, is_active
  Tabel "products"  : id, tenant_id, category_id(->categories), name,
                      description, price, is_available, image_url
  Catatan: tenant_id = UUID penanda cafe (tanpa foreign key, karena beda DB
  dari IAM). Foreign key cuma dipakai relasi internal (produk -> kategori).

ENDPOINT
  PUBLIK (tanpa login):
    GET /api/ping                    -> cek service hidup
    GET /api/menu?tenant=<id-cafe>   -> menu untuk customer
                                        (cuma kategori aktif + produk tersedia)

  KHUSUS OWNER (wajib token + role owner):
    GET    /api/categories           -> daftar kategori
    POST   /api/categories           -> tambah kategori
    PUT    /api/categories/{id}      -> edit kategori
    DELETE /api/categories/{id}      -> hapus kategori
    GET    /api/products             -> daftar produk
    POST   /api/products             -> tambah produk
    PUT    /api/products/{id}        -> edit produk
    DELETE /api/products/{id}        -> hapus produk

ALUR KERJA

  Alur A — Owner kelola menu:
    1. Owner login di IAM -> dapat token (berisi cafe mana + jabatan owner)
    2. Owner kirim "tambah produk Espresso 18rb" + token ke Catalog
    3. Catalog verifikasi token pakai PUBLIC key IAM:
         - token asli? (tanda tangan cocok)
         - jabatannya owner? (kalau kasir -> DITOLAK 403)
    4. Catalog simpan produk, otomatis dicap milik cafe si owner
       (id cafe diambil dari TOKEN, bukan dari input -> gak bisa dipalsuin)

  Alur B — Customer lihat menu (tanpa login):
    1. Customer scan QR cafe A -> buka /api/menu?tenant=A
    2. Catalog ambil kategori aktif + produk tersedia MILIK cafe A saja
    3. Balikin daftar menu rapi (dikelompokkan per kategori)

ATURAN EMAS (dijaga & teruji)
  1. Isolasi antar-cafe: cafe A tak bisa lihat/ubah menu cafe B.
     Akses data cafe lain dijawab "tidak ditemukan" (404).
  2. Cap cafe diambil dari token, bukan input -> anti pemalsuan tenant.
  3. Hanya owner yang boleh mengubah menu (kasir/customer ditolak).
  4. Catalog tak pegang kunci rahasia -> cuma bisa verifikasi, aman.

KEAMANAN DITUNDA (non-kritis): services/catalog/SECURITY_TODO.md
  - Logout/blacklist IAM belum terlihat Catalog sampai token kedaluwarsa (60m).
  - Menu publik belum ada rate limit (tambah sebelum go-live).
  - Belum ada pagination di daftar kategori/produk.

STATUS: SELESAI + 19 feature test lulus. Sudah di-commit (46cee2f). Tabel menu
        masih KOSONG (mesinnya siap, menu tinggal diisi).


================================================================================
  SERVICE 3 — ORDERING  (Pesanan & Kasir)
================================================================================

TUJUAN
  "Mesin pesanan" — tempat pesanan lahir sampai dibayar. Customer scan QR meja,
  pesan sendiri dari HP, lalu kasir yang mengesahkan pembayaran. Ordering yang
  memegang kebenaran "sudah dibayar atau belum" dan menghitung total (harga +
  service charge + PPN).

KONFIGURASI
  - Laravel 13, PHP 8.3+
  - Database: MySQL "fnbsense_ordering" (+ "fnbsense_ordering_test" buat test)
  - Port: 8002
  - Auth: JWT RS256 STATELESS -> sama kayak Catalog, cuma pegang PUBLIC key IAM.
          Endpoint customer TANPA login (dikenali dari QR meja, bukan token).
  - Harga produk TIDAK disimpan sendiri -> selalu diambil dari Catalog saat pesan.

ISTILAH KHUSUS SERVICE INI
  - Outlet    = cabang/gerai satu cafe. Data pesanan dicap per outlet.
  - qr_token  = kode acak di stiker QR tiap meja. Ini yang menentukan pesanan
                masuk ke cafe & meja mana (customer nggak milih sendiri).
  - PENDING   = pesanan sudah masuk, BELUM dibayar.
  - PAID      = sudah dibayar & disahkan kasir. FINAL, tak bisa dibatalkan.
  - Outbox    = "kotak surat keluar". Saat pesanan PAID, ditulis 1 surat event
                buat dikirim ke service lain nanti (potong stok, catat laporan).

STRUKTUR DATA (garis besar)
  Tabel "tables"        : meja + qr_token (per outlet)
  Tabel "order_settings": tarif PPN & service charge + batas waktu, per outlet
  Tabel "orders"        : pesanan (status, total uang, siapa kasir yg sahkan)
  Tabel "order_items"   : rincian item (nama & harga "difoto" saat pesan, biar
                          struk lama tetap benar walau menu berubah nanti)
  Tabel "outbox"        : antrean surat event "sudah dibayar"

ENDPOINT

  CUSTOMER (tanpa login, dibatasi rate limit):
    GET  /api/t/{qr_token}          -> scan meja: ini cafe & meja mana
    POST /api/orders                -> buat pesanan (kirim: meja, item, nama)
    GET  /api/orders/{id}           -> cek status pesanan (buat nungguin)

  KASIR / OWNER (wajib token + role cashier atau owner):
    GET  /api/cashier/orders                       -> antrean pesanan masuk
    GET  /api/cashier/orders/{id}
    POST /api/cashier/orders/{id}/confirm-payment  -> sahkan LUNAS
    POST /api/cashier/orders/{id}/cancel           -> batalkan

  OWNER (kelola meja & tarif):
    GET/POST/PUT/DELETE /api/tables  + /api/tables/{id}/rotate-qr (ganti QR)
    GET/PUT /api/settings            -> atur tarif PPN, service charge, batas waktu

ALUR PAY-FIRST (inti FNBSense)
    1. Customer scan QR meja 5 -> HP-nya buka menu cafe itu.
    2. Pilih item -> kirim. Ordering ambil HARGA dari Catalog (bukan dari HP
       customer), hitung total + service charge + PPN. Status: PENDING.
    3. Pesanan nongol di layar kasir.
    4. Customer bayar (QRIS statis / cash) -> kasir klik "SUDAH BAYAR".
    5. Status jadi PAID + 1 surat outbox ditulis (buat dapur/stok/laporan nanti).

ATURAN EMAS (dijaga & teruji)
  1. Harga & total SELALU dihitung server dari data Catalog. Harga yang dikirim
     HP customer diabaikan -> mustahil "diskon sendiri".
  2. LUNAS itu final. Sekali PAID tak bisa ditarik balik.
  3. Anti bayar-dobel: tombol "sudah bayar" dipencet berapa kali pun tetap 1x
     lunas & 1 surat outbox (idempotent). Ini pengaman uang paling penting.
  4. Sahkan-LUNAS + tulis surat outbox = 1 paket: dua-duanya jadi, atau batal
     dua-duanya. Tak mungkin ada pesanan lunas tanpa suratnya.
  5. Isolasi antar-cafe/outlet: pesanan cafe lain dijawab "tidak ditemukan" (404).
  6. Customer dikenali dari QR meja -> mustahil pesan ke cafe orang lain.

CATATAN
  - Pesanan PENDING yang tak pernah dibayar otomatis jadi EXPIRED (satpam
    terjadwal tiap menit). SUDAH dibuat (L9).
  - Surat outbox sekarang SUDAH dikirim ke antrean pusat (RabbitMQ) oleh
    "tukang pos" (relay). Lihat SERVICE 4 (Realtime) di bawah.

STATUS: SELESAI SEMUA (L1-L10) + teruji (80 test) & di-commit (terakhir: db0242b).
        Kalkulator + endpoint customer + kasir (anti bayar-dobel) + auto-expire
        + test isolasi. F2 (Ordering) KELAR.


================================================================================
  SERVICE 4 — REALTIME  (Pipa Event & Layar Dapur / KDS)  — service Node PERTAMA
================================================================================

TUJUAN
  "Papan pengumuman dapur". Begitu pesanan LUNAS di Ordering, kabarnya harus
  langsung sampai ke dapur (nanti juga ke stok & laporan). Realtime mengalirkan
  kabar itu dan menampilkannya realtime di layar dapur (KDS = Kitchen Display
  System).

KENAPA NODE (BUKAN LARAVEL)?
  Layar dapur nyambung terus seharian (koneksi "hidup" lama tapi sering diam).
  Node enteng megang ribuan koneksi diam sekaligus; PHP boros buat model ini.
  Ini service Node PERTAMA di FNBSense (lainnya PHP). Bahasa beda tetap nyambung
  karena lewat "bahasa bersama": antrean RabbitMQ + token JWT, bukan lewat
  bahasa pemrograman.

KONFIGURASI
  - Node + TypeScript
  - Nyambung ke: RabbitMQ (antrean event) + verifikasi token JWT (PUBLIC key IAM)
  - Port WebSocket: 8081
  - TIDAK punya database sendiri (cuma penerus + penyiar kabar)

DUA BAGIAN

  BAGIAN A — "Tukang pos" (relay, ada di dalam service Ordering)
    Perintah "outbox:relay" mengangkat surat dari kotak outbox -> kirim ke
    kantor pos pusat (RabbitMQ). Ditandai "terkirim" HANYA kalau kantor pos
    benar-benar menerima (biar tak ada surat hilang diam-diam).

  BAGIAN B — "Penyiar dapur" (service Realtime/Node)
    Ambil surat "sudah dibayar" dari RabbitMQ -> siarkan ke layar dapur yang
    tersambung, HANYA ke dapur outlet yang benar.

ALUR
    Pesanan LUNAS (Ordering) -> surat outbox
      -> tukang pos (relay) angkat -> RabbitMQ (kantor pos)
      -> penyiar (Node) ambil -> broadcast ke layar dapur outlet itu (WebSocket)

ATURAN EMAS (dijaga)
  1. Tak ada surat hilang diam-diam: ditandai terkirim hanya setelah kantor pos
     konfirmasi (kirim-minimal-sekali).
  2. Anti dobel: surat sama sampai dua kali -> yang kedua dibuang (dikenali dari
     nomor unik surat / event_id).
  3. Layar dapur wajib bawa token sah buat nyambung (kalau tidak -> ditolak).
  4. Kabar outlet A tak nyasar ke dapur outlet B (dipisah per outlet).

BELUM DIBUAT (sengaja, catatan jujur)
  - Anti-dobel masih "ingatan sesaat" (hilang kalau service restart).
  - Layar dapur (frontend) belum dibuat -> baru mesin penyiarnya.
  SUDAH DIKERASKAN:
  - "Denyut" koneksi (heartbeat) SUDAH ada (commit 3897be1): server ping tiap
    30 detik, koneksi dapur yang tak balas dianggap mati & diputus bersih.

STATUS: F3a (pipa event) + F3b (layar KDS + auth) SELESAI & terbukti jalan
        end-to-end. Di-commit: a66f9a5, c2c599c, 5c7fd3c. Printing/struk (F3c)
        DITUNDA (layar KDS menggantikan tiket dapur untuk sekarang).


================================================================================
  SERVICE 5 — INVENTORY  (Stok Gudang & Bahan Baku)
================================================================================

TUJUAN
  "Buku stok gudang". Nyatet sisa bahan baku tiap cabang (susu, kopi, gula, ...)
  dan — nanti — memotongnya otomatis tiap ada pesanan LUNAS. Jadi owner tahu
  bahan mana mau habis tanpa hitung manual.

KENAPA SERVICE TERPISAH?
  Stok itu urusan sendiri: angkanya berubah tiap transaksi, butuh kejujuran
  angka (tak boleh bocor/dobel). Dipisah biar Ordering fokus ke uang, Inventory
  fokus ke barang. Inventory "mendengar" kabar LUNAS dari pipa event yang sama
  (RabbitMQ) — sama kayak layar dapur.

KONFIGURASI
  - Laravel 13, PHP 8.3+
  - Database: MySQL "fnbsense_inventory" (+ "fnbsense_inventory_test" buat test)
  - Port: 8003
  - Auth: JWT RS256 STATELESS -> cuma pegang PUBLIC key IAM (verifikasi doang).
          TAMBAHAN: token WAJIB bawa "cabang mana" (outlet_id) — kalau tidak,
          ditolak. Stok selalu milik satu cabang, jadi tanpa itu tak masuk akal.

ISTILAH KHUSUS SERVICE INI
  - Bahan (ingredient) = barang mentah (susu, kopi). Daftarnya DIBIKIN di Catalog,
                         bukan di sini (biar satu sumber, tak dobel-input).
  - Resep (BOM)        = "1 Latte butuh 200ml susu + 18gr kopi". Juga di Catalog.
  - Saldo stok         = sisa bahan sekarang di satu cabang.
  - Buku gerakan (ledger) = catatan tiap stok naik/turun (+5000 belanja masuk,
                         -200 kepakai). Saldo = hasil jumlah buku ini, bukan
                         angka yang diketik bebas -> selalu bisa dilacak.
  - Opname             = hitung stok fisik, cocokkan dengan sistem.

STRUKTUR DATA
  Tabel "stock_balances"  : saldo tiap bahan per cabang (sisa sekarang + batas
                            minimum). Satu bahan cuma boleh 1 baris per cabang.
  Tabel "stock_movements" : BUKU GERAKAN. Tiap perubahan = 1 baris (naik/turun,
                            alasannya: belanja masuk / opname / kepakai pesanan).
  Tabel "processed_orders": "buku absen" pesanan yang stoknya sudah dipotong ->
                            pagar biar 1 pesanan tak dipotong dua kali.
  Catatan: master bahan & resep TIDAK di sini -> Inventory nanya ke Catalog
  lewat "kunci rahasia antar-service" (X-Service-Token), bukan token user.

ENDPOINT
  PUBLIK:
    GET /api/ping                    -> cek service hidup

  KHUSUS OWNER (wajib token + role owner + cabang):
    GET  /api/stock                  -> lihat saldo stok cabang ini
    POST /api/stock/restock          -> barang masuk (belanja) -> saldo naik
    POST /api/stock/adjust           -> opname: input hasil hitung fisik ->
                                        sistem catat selisihnya sendiri

  BUKAN ENDPOINT (tapi "kuping" event — SUDAH JADI, F4b):
    daemon "php artisan inventory:consume" -> dengar event "sudah dibayar" dari
    RabbitMQ -> baca resep dari Catalog -> potong bahan otomatis.

ALUR KERJA

  Alur A — Barang masuk (belanja):
    1. Owner belanja 5 liter susu -> input "restock susu +5000ml".
    2. Inventory tambah saldo + tulis 1 baris buku gerakan (+5000, "belanja").
    3. Bahan baru muncul otomatis pas pertama di-restock (tak perlu daftar ulang;
       daftarnya sudah di Catalog).

  Alur B — Opname (cocokkan fisik):
    1. Owner hitung fisik: susu tinggal 4800ml (sistem kira 5000).
    2. Input "counted_qty 4800" -> sistem catat selisih -200 di buku gerakan,
       saldo dikoreksi jadi 4800. Kalau pas (tak ada selisih) -> buku tak dikotori.

  Alur C — Potong otomatis (SUDAH JADI & teruji E2E, F4b):
    Pesanan LUNAS -> Inventory dengar dari RabbitMQ -> tanya Catalog "resepnya
    apa?" -> potong tiap bahan sesuai resep x jumlah pesanan -> tulis buku gerakan
    + tandai "sudah diproses". Kabar sama datang dua kali -> dibuang, tak dobel.

    Kalau Catalog lagi MATI pas ada pesanan masuk: potongannya DITUNDA (kabarnya
    dibalikin ke antrean), BUKAN hilang -> begitu Catalog hidup lagi, otomatis
    diproses. (Terbukti live pas uji F4d: consumer nunggu Catalog dinyalakan dulu,
    baru stok kepotong.) Uang sudah masuk, jadi stok tak boleh diam-diam lolos.

  Alur D — Saga stok kurang / resep kosong (SUDAH JADI, F4c):
    - Stok kurang -> tetap dipotong, saldo boleh MINUS (sinyal jujur "harus
      restock") + tembak alarm "inventory.shortfall". Pesanan LUNAS tak batal.
    - Bahan mau habis (lewat batas minimum) -> alarm dini "inventory.low_stock".
    - Produk belum punya resep -> dilewati + alarm "inventory.recipe_missing",
      consumer TAK ikut mati. Alarm cuma bunyi pas MELINTAS batas (bukan tiap
      pesanan) -> owner tak dibanjiri notif kembar.

ATURAN EMAS (yang sudah jadi, dijaga & teruji)
  1. Saldo = hasil buku gerakan, BUKAN angka ketik bebas. Tiap perubahan
     terekam -> bisa dilacak "kok sisanya segini, dari mana aja".
  2. Cuma owner yang boleh kelola stok (kasir/customer ditolak).
  3. Isolasi per cabang: stok cabang A tak tercampur cabang B. "Cabang mana"
     diambil dari TOKEN, bukan input -> owner tak bisa nyentuh stok cabang lain.
  4. Tiap perubahan = 1 paket utuh (saldo + buku gerakan jadi bareng, atau batal
     bareng) + dikunci saat diubah -> dua belanja barengan tak saling menimpa.

ATURAN EMAS (F4b/F4c — sudah jadi, dijaga & teruji E2E)
  5. Anti potong-dobel: 1 pesanan lunas cuma memotong stok SEKALI (dijaga "buku
     absen" processed_orders), walau kabarnya datang dua kali. (Terbukti F4d.)
  6. Stok kurang tetap dipotong (saldo boleh minus) sebagai sinyal jujur "harus
     restock" -> pesanan LUNAS TIDAK dibatalkan (uang sudah masuk, itu final).

BELUM DIBUAT (sengaja, catatan jujur)
  - Validasi "bahan ini beneran ada di Catalog?" saat restock -> masih ditunda.
    Owner pilih dari daftar, jadi risiko salah-ketik kecil.
  - Frontend kelola stok & layar alarm stok belum dibuat -> baru mesinnya.
  - Uji rantai HARFIAH lewat Ordering (bayar di kasir -> relay) belum dijalankan;
    F4d dibuktikan dengan menyuntik event langsung (jalur relay-nya sendiri sudah
    terbukti di F3a). Risiko rendah.
  - Variant/addon (mis. "extra shot") belum ikut dipotong -> nunggu Catalog punya.

CATATAN JUJUR (utang yang diakui)
  - "Cabang mana" (outlet_id) belum bisa diisi IAM untuk akun owner -> sama
    penghalang yang menahan Ordering. Inventory sudah dipasang PENJAGA: token
    tanpa cabang langsung ditolak (gagal aman, bukan bocor diam-diam).
